# Limites connues du périmètre MVP

À communiquer explicitement à toute organisation évaluant un déploiement MVP (`docs/roadmap.md` §2) :

| Limite | Compensée par | Résolue en |
|---|---|---|
| ~~Pas de MFA natif~~ — **TOTP natif pour les rôles déclarés** (ADR-0062). **Il reste** : ~~pas de WebAuthn~~ (ADR-0065 ; TOTP se laisse toujours hameçonner, mais il ne compte plus pour les rôles de `MFA_PHISHING_RESISTANT_ROLES`) ; pas de codes de secours ; ~~l'émission d'un code d'enrôlement et la remise à zéro ne sont pas à l'audit~~ (ADR-0064) ; pas de QR code dans l'Admin UI ; le second facteur est vérifié à la connexion, pas pendant la vie du jeton (1 h) ; perdre `MFA_SECRET_KEY_HEX` rend tous les secrets illisibles | `MFA_REQUIRED_ROLES` sur les rôles puissants ; codes d'enrôlement transmis par un autre canal ; sauvegarde de `MFA_SECRET_KEY_HEX` hors de la base | ~~WebAuthn~~ (ADR-0065) ; codes de secours : à décider |
| **WebAuthn (ADR-0065)** : second facteur lié à l'origine, seul admis pour les rôles stricts. **Il reste** : ~~une seule clé par compte~~ (ADR-0066 : clé de secours avec la clé actuelle et un code d'administrateur ; révocation à l'unité par l'administrateur) ; l'utilisateur ne révoque pas lui-même une clé ; attestation `none` (aucun modèle d'authentificateur exigé) ; vérification de l'utilisateur (PIN, biométrie) demandée, pas exigée ; un rôle strict ne se connecte que par un navigateur, sur une origine déclarée ; pas de passkey sans mot de passe ; une dépendance de plus (`go-webauthn` et sept modules) | `MFA_PHISHING_RESISTANT_ROLES` sur les rôles puissants ; `WEBAUTHN_ORIGINS` tenu à jour | ~~Clé de secours~~ (ADR-0066) ; liste de modèles (AAGUID), passkeys sans mot de passe : à décider |
| **Les connexions à l'audit (ADR-0064)** : chaque jeton est écrit (`auth.login`, `auth.login_mfa`) avant d'être émis ; les gestes du second facteur avant d'être faits ; les refus au mieux, dans un budget par nom. **Il reste** : **l'Audit Service devient une dépendance de toute connexion** — en panne, personne ne se connecte, l'administrateur local compris ; les refus au-delà du budget ne sont pas dans la chaîne, et le budget est par processus ; le nom d'un refus est une chaîne choisie par l'attaquant (bornée, désarmée) ; la vérification d'un jeton à chaque requête n'est pas écrite | L'Audit Service aussi disponible que l'Authentication Service ; surveiller les `503` de `/auth/login` | — |
| **Pointeur dessiné dans l'image (ADR-0091, incréments 1–2)** : en RDP, le pointeur de la cible est dessiné dans chaque image, montrée et enregistrée (`SCREEN_DRAW_POINTER`, allumé par défaut). **Il reste** : en VNC, le pointeur n'est pas encore dessiné ; l'Admin UI affiche encore la flèche du navigateur par-dessus celle de l'image, si bien que l'opérateur voit deux pointeurs, l'un en retard ; formes 1, 24 et 32 bpp seulement, toute autre ferme la session ; l'alpha est lu comme non prémultiplié | `SCREEN_DRAW_POINTER=false` rend le comportement antérieur | ADR-0091, incréments 3 (VNC) et 4 (Admin UI) |
| Pas de validation multi-étapes | RBAC seul avant octroi | v0.0.1 (Workflow/Approval Engine) |
| Le périmètre protocolaire reste partiel : SSH et VNC sont raccordés au runtime ; RDP est disponible derrière `RDP_ENABLED=true` au Broker et au proxy (désactivé par défaut) ; les autres protocoles annoncés ne sont pas encore livrés | Aucun accès direct aux cibles ; seuls les protocoles explicitement activés et proxifiés sont exposés | v0.0.1/v0.0.2 et incréments ultérieurs |
| Le runtime `cmd/rdp-vnc-proxy` raccorde Vault, Audit, Video Recorder gRPC et `proxycore.ServeScreen`; tickets proxy à usage unique, révocation, entrée binaire bornée et `END` terminal sont implémentés. Le Broker route par protocole (`ssh`, `vnc`, et `rdp` quand `RDP_ENABLED=true`, ADR-0088) et la Gateway relaie le WebSocket same-origin avec cookie HttpOnly/SameSite=Strict. Le socle RDP inclut X.224/HYBRID, TLS épinglé, TSRequest DER borné, SPNEGO NTLM strict, NTLMv2 avec MIC et channel binding TLS, GSS_Wrap directionnel, orchestration CredSSP v5/v6, validation `pubKeyAuth` serveur puis délégation `TSPasswordCreds` dans `authInfo` scellé (incrément 16), Basic Settings Exchange MCS/GCC (incrément 17), Channel Connection MCS (Erect Domain, Attach User, Channel Join utilisateur puis I/O, incrément 18), Client Info Unicode sur le canal global I/O 1003 ; mot de passe auto-logon dans TS_INFO_PACKET sous TLS, non conservé dans la session (incrément 20), Licensing Personal Terminal Server (Server License Request, Client New License Request RSA, acceptation stricte de STATUS_VALID_CLIENT/ST_NO_TRANSITION, incrément 21), codec Demand Active/Confirm Active avec validation stricte des capacités (incrément 19), puis finalisation RDP (Synchronize, Control Cooperate/Request Control, Font List et validation des réponses serveur jusqu’à Font Map, incrément 22). Le passage aux capacités est désormais débloqué uniquement après une séquence Licensing réelle validée ; la session n’est déclarée finalisée qu’après Font Map. **Il reste** : CAL/RDS complet (émission, mise à niveau, Platform Challenge), certificats propriétaires legacy, identités Licensing non ASCII, interopérabilité Windows/RDS ; les fragments TPKT restent plafonnés à 16 383 octets et le Share Data PDU réassemblé à 65 535 octets ; décodeurs slow-path OpaqueRect strict (incrément 34), PatBlt limité à PATCOPY/PATINVERT/PATAND/PATOR/NOTPATCOPY avec BS_SOLID (incréments 35, 38, 39 et 40) et DstBlt limité à BLACKNESS/WHITENESS (incrément 36) et DSTINVERT stateful (incrément 37), MultiDstBlt limité à BLACKNESS/WHITENESS/DSTINVERT avec liste delta stricte de 45 rectangles maximum (incrément 42) ; MultiOpaqueRect limité à neuf champs explicites et 45 rectangles delta maximum (incrément 43) ; MultiPatBlt limité aux cinq ROP solides et à une brosse BS_SOLID canonique (incrément 44) ; MultiScrBlt limité à SRCCOPY et à des rectangles source/destination strictement bornés (incrément 45) ; LineTo limité à R2_BLACK/R2_COPYPEN/R2_NOT/R2_XORPEN/R2_NOTXORPEN/R2_NOP/R2_WHITE et une plume solide d’un pixel, sans clipping (incréments 46, 52, 54, 57 et 58) ; Polyline limité à R2_BLACK/R2_COPYPEN/R2_NOT/R2_XORPEN/R2_NOTXORPEN/R2_NOP/R2_WHITE, 34 points et 148 octets (incréments 47, 53, 55, 57 et 58) ; PolygonSC limité à R2_BLACK/R2_COPYPEN/R2_NOT/R2_XORPEN/R2_NOTXORPEN/R2_NOP/R2_WHITE et ALTERNATE, 34 deltas et 147 octets de données (incréments 48, 57 et 58), index 20 non annoncé ; EllipseSC limité à R2_BLACK/R2_COPYPEN/R2_NOT/R2_XORPEN/R2_NOTXORPEN/R2_NOP/R2_WHITE et ALTERNATE, rectangle inclusif 16 bits et 13 octets de champs (incréments 49, 57 et 58), index 25 non annoncé, parité GDI pixel-à-pixel non vérifiée ; coordonnées d'ordre absolues, liste delta bornée sans clipping, aucun champ omis accepté ; l'index DstBlt 0, le slot partagé PatBlt/OpaqueRect index 1 et l'index MultiDstBlt 15 restent non annoncés car ces profils ne couvrent pas toutes les variantes normatives ; les autres ordres restent absents, ainsi que les événements Fast-Path pointeur/clavier/souris ; le codec est activé dans le runtime par `RDP_ENABLED=true`, au Broker et au proxy, éteint par défaut (ADR-0088) ; les plans RDP6 ARGB RAW/RLE et leur raccordement au ScreenCodec sont implémentés (incréments 23–30) ; la réception Fast-Path Bitmap Update non fragmentée et non compressée est décodée (incrément 31), mais FASTPATH_OUTPUT_SUPPORTED n’est pas annoncé ; les profils AYCoCg CLL avec et sans subsampling sont décodés en RAW/RLE (incréments 32–33) ; les autres événements Fast-Path et la compression Fast-Path restent refusés ; la fragmentation Fast-Path est réassemblée jusqu’à 256 Kio, éprouvée contre Windows (ADR-0071) ; carte à puce/Remote Guard, Kerberos et SPNEGO MIC ne sont pas pris en charge ; les essais Windows/RDS sont limités aux scénarios explicitement couverts par le workflow `.github/workflows/windows-rdp.yml` et ne constituent pas une garantie de compatibilité générale ; le parcours VNC de bout en bout est validé ; Le runtime exige `TARGET_TLS_ROOTS_FILE` explicite et la route RDP est conditionnelle à `RDP_ENABLED=true` au Broker et au proxy, désactivée par défaut (ADR-0088) | Le pin TLS précède toute preuve NTLM ; le mot de passe n'est jamais transmis en clair et `TSCredentials` est scellé après le binding ; les erreurs d'état ferment le transport et abandonnent le contexte GSS_Wrap | Capacités et validation Windows/RDS réelle selon ADR-0071 |
| **Relais écran durci (ADR-0071, incrément 66)** : un certificat de cible différent du pin écrit `session.tls_certificate_mismatch` ; l'entrée d'une session est bornée (`SCREEN_INPUT_RATE_PER_SECOND`, `SCREEN_INPUT_BURST`) ; un navigateur qui ne lit plus ne bloque ni l'enregistrement ni la fin de session ; un recorder muet plus de 10 s vaut `session.recording_lost` ; une autre origine ne peut pas consommer le cookie d'attache. **Il reste** : le budget d'entrée compte par session sur une seule instance du proxy ; une frame acquittée peut ne jamais être montrée à un opérateur lent, elle reste dans l'enregistrement. | connu |
| **Session VNC de bout en bout (ADR-0071, incrément 67)** : Admin UI, Gateway, Broker, Vault, proxy et Video Recorder réels jusqu'à TigerVNC 1.13.1 ; image affichée identique à l'octet à l'image rejouée. Les refus de §5 et §12 portent leur code de bout en bout, et la pile `deploy/docker-compose` avec ses profils `recording` et `rdp-vnc` est éprouvée (`make test-compose`, clé locale du recorder et non Transit). `deploy/base44` ouvre aussi cet écran et une session SSH sur `acc_demo` (l'Admin UI n'a pas de bouton de connexion SSH : API et client SSH), avec un clavier vérifié sur l'écran de la cible (`TestBase44Preview`, pile démarrée à la main ; hors CI). **Il reste** : un mot de passe refusé par la cible se dit `target_unreachable`, §12 n'ayant pas de code pour ce cas ; `up --wait` ne vérifie ni le recorder ni le proxy d'écran, sans healthcheck ; lecteur de l'écran enregistré dans l'Admin UI, sans export vidéo ni recherche dans l'image ; RealVNC refusé (RFB 5.0) ; aucun presse-papiers ; raccourcis réservés au navigateur non transmis, sauf Ctrl+Alt+Suppr, envoyé à une session RDP par un bouton (ADR-0071) et éprouvé contre Windows ; les touches étendues (pavé numérique, AltGr, Suppr) arrivent, mais la touche Windows seule n'ouvre pas le menu Démarrer d'une cible Windows (Ctrl+Échap l'ouvre), cause non établie ; écran illisible au lecteur d'écran ; RDP ouvert aux opérateurs seulement si l'exploitant met `RDP_ENABLED=true` au Broker et au proxy (ADR-0088 ; parcours de bout en bout depuis l'API publique contre FreeRDP 3, `make test-rdp-recording`) : les critères de sortie restants d'ADR-0071 sont tenus (le texte, rendu par bitmaps, est lisible sans cache de glyphes, ADR-0089) ; les dispositions QWERTY et AZERTY sont vérifiées contre Windows (incrément 77) ; une image de plus de 4 Mio, RDP comme VNC, ferme la session en `recording_lost`, auditée (incrément 76) ; et le clavier passe par les touches physiques (scancodes) ; `pkg/rdp` ouvre une session complète contre FreeRDP 3.15 (image, souris, clavier, `make test-rdp-interop`) et, contre Windows Server 2022 (dockur, CI `windows-rdp.yml`), passe CredSSP, MCS, les canaux, le Client Info, la licence et l'échange de capacités. Ce Windows, laissé par défaut (`RDP-Tcp\ColorDepth` 3, `fInheritColorDepth` 0, mesurés), propose 16 bpp à ce client, qui n'annonce pas le pipeline graphique : le client décode désormais 15 et 16 bpp (non compressé et Interleaved RLE, ADR-0086), et refuse 8 et 24 bpp. Une session en 16 bpp n'a que 65 536 couleurs, à l'écran comme dans l'enregistrement ; l'opérateur qui veut 32 bpp l'autorise sur la cible (stratégie « Limit maximum color depth »). Une session ouverte par Windows avec les identifiants délégués se reconnaît à sa notification d'ouverture (`LogonNotified`), que le test exige ; la reprise d'une session déjà ouverte sur la cible, déconnectée ou active à la console, est validée sur un passage (ADR-0071) ; des touches envoyées dans les millisecondes qui suivent un clic changeant le focus peuvent être perdues par Windows (mesuré, un Synchronize Event n'y change rien), aucune au rythme d'une personne ; la fidélité des pixels à fort contraste n'est pas prouvée, un bogue de l'encodeur de FreeRDP la masquant ; un redimensionnement du bureau par le serveur est suivi (réactivation, incrément 72 : éprouvée contre FreeRDP, jamais rencontrée chez Windows) ; l'enregistrement d'une session RDP est éprouvé de bout en bout sans exposer RDP (incrément 73, `make test-rdp-recording` : proxy et Video Recorder réels, FreeRDP 3 ; image montrée identique à l'octet à l'image rejouée, enregistrement scellé, à travers un changement de taille en cours de session), depuis l'API publique quand RDP est allumé (ADR-0088) ; contre Windows Server 2022, l'enregistrement est établi aux trois cibles du CI (PR #93), et la réactivation n'y est jamais arrivée. | connu |
| L'identité S3 du Video Recorder a `Admin` sur l'instance SeaweedFS dédiée pour créer son bucket au démarrage ; un processus compromis peut donc aussi supprimer ou reconfigurer les buckets de cette instance | Instance SeaweedFS non publiée, réseau Compose interne, volume et identifiants réservés au Video Recorder | Séparer l'initialisation du bucket de l'identité de service et limiter les droits aux objets du bucket |
| L'activation de l'ancien profil Compose `recording` utilise brièvement `PG_SUPERUSER_PASSWORD` dans un job d'initialisation pour créer le rôle et la base du Video Recorder ; un job compromis pendant cette étape pourrait agir comme superutilisateur PostgreSQL | Job ponctuel, aucune publication de port, réseau interne Compose, secret limité à cette étape | Remplacer le bootstrap par une migration administrative dédiée au déploiement, sans transmettre le mot de passe superutilisateur |
| Pas de détection d'anomalie/score de risque | Aucune | v0.0.2 |
| Le Command Recorder est une dépendance de disponibilité de **tous** les accès privilégiés (ADR-0008) : s'il est indisponible, aucune session ne s'ouvre et les sessions en cours s'arrêtent à leur prochaine commande | Déployer le recorder et sa base en haute disponibilité (`docs/deployment/high-availability.md`), alerter sur `/readyz` ; en dernier recours, la dérogation break-glass (ADR-0009, désactivée par défaut) | Réduite par ADR-0009 ; la dépendance demeure pour toute session ordinaire |
| ~~Une seule personne suffit à obtenir un break-glass~~ — **fermé par défaut** (ADR-0011) : la demande attend l'approbation d'une autre personne. Reste : **pas de revue obligatoire après l'incident**, un seul approbateur (pas de quorum), et `BREAKGLASS_APPROVAL=disabled` rétablit l'ancien comportement (annoncé au démarrage, à ne pas laisser en production) | Revue de `session.breakglass_requested` / `_approved` / `_rejected` / `session.breakglass` après chaque usage ; ne pas activer `disabled` | Revue post-incident : v0.0.1 (Workflow/Approval Engine) |
| Deux comptes tenus par la même personne, ou deux personnes complices, contournent la double validation : la règle compare des identifiants, pas des humains | Un compte par personne, rôles de demande et d'approbation **disjoints**, revue des politiques `breakglass-approve:*`, provisionnement (SCIM) | Non prévue — hygiène des identités |
| ~~Aucune liste ni notification des demandes en attente~~ — **fermé** (ADR-0012) : `GET /sessions?status=pending_approval` donne à l'approbateur ce qu'il peut décider, et un webhook optionnel le prévient. Reste : **aucune nouvelle tentative** (une notification perdue est perdue, la liste est le filet), **un seul canal sans routage par personne** (les membres du canal apprennent qu'une demande existe, pour quel compte et de qui ; pas la justification), **message signé seulement si `BREAKGLASS_NOTIFY_SECRET` est fixé** (sinon l'URL est le seul secret ; Slack et Teams ignorent la signature de toute façon) — le plafond par demandeur est venu d'ADR-0013, voir la ligne suivante | Alerter sur les `session.breakglass_requested` en rafale ; revue des politiques `breakglass:*` ; canal restreint aux astreintes | Signature et plafond : fermés par ADR-0013 ; nouvelle tentative et routage par personne : Notification Service (v0.0.1) |
| Le plafond de demandes en attente est **par demandeur** (ADR-0013) : K identités qui détiennent les deux politiques occupent K × N places ; un demandeur au plafond **ne peut plus rien demander** pendant la fenêtre d'approbation (15 minutes par défaut) — un compte dont on a dérobé le jeton peut donc, en remplissant sa propre file, empêcher son titulaire de demander ; deux comptes, deux plafonds ; ~~les tentatives **refusées** ne sont pas limitées en débit~~ — **fermé pour `POST /sessions`** (ADR-0014, voir la ligne suivante) ; **un seul secret de signature, sans chevauchement de rotation** ; aucun identifiant de livraison ; aucun récepteur tiers réel n'a été essayé (le récepteur des tests est écrit d'après la description du contrat) | Alerter sur les rafales de `session.breakglass_requested` avec `success=false` ; restreindre le rôle de demande ; changer le secret des deux côtés pendant une plage calme ; vérifier côté récepteur avec la tolérance la plus courte supportable | Rotation à deux secrets : à décider |
| Le budget de `POST /sessions` est **par identité et par processus** (ADR-0014) : K jetons compromis, K budgets ; *N* réplicas du Gateway, *N* fois le budget ; un jeton volé peut **priver son titulaire** de son budget (un jeton se reforme toutes les 10 secondes avec les défauts, il va à qui arrive le premier) ; **les refus de débit ne sont pas dans l'audit**, seulement dans le journal du Gateway ; **seuls `POST /sessions`, `approve`, `reject`, `connect` et `DELETE /sessions/{id}` sont limités par identité** (ADR-0016 puis ADR-0017 pour les quatre dernières, dans un seau à part) — les lectures (dont la liste des demandes en attente, qui coûte un appel à l'Authorization Service par compte distinct) ne le sont que par adresse ; **terminer en masse est ralenti** (vingt sessions d'un coup épuisent le budget d'actions) ; **en urgence, un jeton volé pèse plus** : qui détient celui d'un approbateur ou d'un demandeur peut épuiser son budget d'actions pendant l'incident ; le budget d'actions est celui de l'utilisateur, pas d'une session (un script qui en traite vingt d'un coup est ralenti) ; valeurs par défaut choisies, non mesurées sur un usage réel | Alerter sur les lignes de journal « the session requests of user … are refused » et « the session actions of user … are refused » ; **révoquer le jeton** plutôt que relever la limite ; un état partagé (Redis) bornerait le budget entre réplicas | Budget sur les lectures (si une mesure montre une charge) ; état partagé entre réplicas : à décider |
| ~~**Les limites par adresse sont fausses derrière Traefik**~~ (ADR-0014) — **fermé si l'opérateur le règle** (ADR-0015) : avec `TRUSTED_PROXY_CIDRS` sur l'arête, chaque client réel a son seau. **Par défaut rien ne change** (personne n'est de confiance, tous les utilisateurs partagent le seau de l'adresse de Traefik ; le Gateway l'annonce au démarrage) ; **la confiance est celle de l'opérateur** : un réseau trop large laisse tout hôte qu'il contient choisir sa clé (seule la longueur 0 est refusée), et un proxy qui n'ajoute pas l'adresse qu'il voit rend l'en-tête forgeable ; **Traefik n'a pas été essayé** (les tests jouent le proxy) ; **une adresse n'est pas une personne** (NAT : un seau pour beaucoup ; beaucoup d'adresses : beaucoup de seaux, donc **aucune borne sur une force brute distribuée**) ; **le /64 IPv6 est un choix non réglable** ; **les refus par adresse ne sont ni audités ni journalisés** (visibles dans le journal d'accès de l'arête) ; par processus | Déclarer le plus **étroit** réseau possible ; faire la vérification de `docs/administration/` (login avec un `X-Forwarded-For` différent à chaque fois : la sixième tentative doit être refusée) ; régler `forwardedHeaders` de Traefik ; alerter sur les `429` du journal d'accès de l'arête | Limite par compte de login (force brute distribuée) ; protocole PROXY ; essai sur un vrai Traefik : à décider |
| ~~Une demande non décidée expire sans événement d'audit (pas de Scheduler pour le déclencher)~~ — depuis ADR-0034, le balayage du Broker la marque `expired` et écrit `session.expire` ; une décision perdante dans une course entre réplicas laisse son événement (`session.breakglass_approved` en double, `decidedBy` nomme le gagnant) | La demande, elle, est auditée ; le statut se lit `expired` ; on préfère un événement en trop à un octroi sans trace | Non prévue — choix assumé (ADR-0011) |
| ~~`terminate` n'avait ni contrôle d'appartenance ni politique propre~~ — **fermé** (ADR-0017) : le demandeur, ou une politique `session-terminate:account:{id}`. ~~**Mais terminer ne coupait pas ce qui est déjà ouvert**~~ — **fermé** (ADR-0018) : le proxy coupe les connexions et jette les tickets avant que le Broker marque la session terminée. **Il reste** : les octrois de portée du Vault ne sont pas révoqués (jeton à usage unique, réservé à l'identité du proxy, abandonné avec le ticket) ; ~~le proxy SSH est en **instance unique** (avec plusieurs réplicas, la révocation n'en atteindrait qu'un)~~ — **fermé** (ADR-0046) : le Broker connaît toutes les instances (`SSH_PROXY_URLS`), chacune annonce son adresse (`SSH_PUBLIC_ENDPOINT`), et la session est révoquée chez toutes ; une seule injoignable empêche de terminer ; la mémoire des révocations est en mémoire (perdue au redémarrage, sans danger puisque le Broker n'émet plus de ticket) ; si le proxy est injoignable on ne peut **pas** terminer (`503`, mode strict).
