# Limites connues du périmètre MVP

À communiquer explicitement à toute organisation évaluant un déploiement MVP (`docs/roadmap.md` §2) :

| Limite | Compensée par | Résolue en |
|---|---|---|
| ~~Pas de MFA natif~~ — **TOTP natif pour les rôles déclarés** (ADR-0062). **Il reste** : ~~pas de WebAuthn~~ (ADR-0065 ; TOTP se laisse toujours hameçonner, mais il ne compte plus pour les rôles de `MFA_PHISHING_RESISTANT_ROLES`) ; pas de codes de secours ; ~~l'émission d'un code d'enrôlement et la remise à zéro ne sont pas à l'audit~~ (ADR-0064) ; pas de QR code dans l'Admin UI ; le second facteur est vérifié à la connexion, pas pendant la vie du jeton (1 h) ; perdre `MFA_SECRET_KEY_HEX` rend tous les secrets illisibles | `MFA_REQUIRED_ROLES` sur les rôles puissants ; codes d'enrôlement transmis par un autre canal ; sauvegarde de `MFA_SECRET_KEY_HEX` hors de la base | ~~WebAuthn~~ (ADR-0065) ; codes de secours : à décider |
| **WebAuthn (ADR-0065)** : second facteur lié à l'origine, seul admis pour les rôles stricts. **Il reste** : ~~une seule clé par compte~~ (ADR-0066 : clé de secours avec la clé actuelle et un code d'administrateur ; révocation à l'unité par l'administrateur) ; l'utilisateur ne révoque pas lui-même une clé ; attestation `none` (aucun modèle d'authentificateur exigé) ; vérification de l'utilisateur (PIN, biométrie) demandée, pas exigée ; un rôle strict ne se connecte que par un navigateur, sur une origine déclarée ; pas de passkey sans mot de passe ; une dépendance de plus (`go-webauthn` et sept modules) | `MFA_PHISHING_RESISTANT_ROLES` sur les rôles puissants ; `WEBAUTHN_ORIGINS` tenu à jour | ~~Clé de secours~~ (ADR-0066) ; liste de modèles (AAGUID), passkeys sans mot de passe : à décider |
| **Les connexions à l'audit (ADR-0064)** : chaque jeton est écrit (`auth.login`, `auth.login_mfa`) avant d'être émis ; les gestes du second facteur avant d'être faits ; les refus au mieux, dans un budget par nom. **Il reste** : **l'Audit Service devient une dépendance de toute connexion** — en panne, personne ne se connecte, l'administrateur local compris ; les refus au-delà du budget ne sont pas dans la chaîne, et le budget est par processus ; le nom d'un refus est une chaîne choisie par l'attaquant (bornée, désarmée) ; la vérification d'un jeton à chaque requête n'est pas écrite | L'Audit Service aussi disponible que l'Authentication Service ; surveiller les `503` de `/auth/login` | — |
| Pas de validation multi-étapes | RBAC seul avant octroi | v0.0.1 (Workflow/Approval Engine) |
| Un seul protocole (SSH) | Périmètre volontairement restreint pour prouver l'invariant (`docs/roadmap.md` §1) | v0.0.1/v0.0.2 |
| Pas de détection d'anomalie/score de risque | Aucune | v0.0.2 |
| Le Command Recorder est une dépendance de disponibilité de **tous** les accès privilégiés (ADR-0008) : s'il est indisponible, aucune session ne s'ouvre et les sessions en cours s'arrêtent à leur prochaine commande | Déployer le recorder et sa base en haute disponibilité (`docs/deployment/high-availability.md`), alerter sur `/readyz` ; en dernier recours, la dérogation break-glass (ADR-0009, désactivée par défaut) | Réduite par ADR-0009 ; la dépendance demeure pour toute session ordinaire |
| ~~Une seule personne suffit à obtenir un break-glass~~ — **fermé par défaut** (ADR-0011) : la demande attend l'approbation d'une autre personne. Reste : **pas de revue obligatoire après l'incident**, un seul approbateur (pas de quorum), et `BREAKGLASS_APPROVAL=disabled` rétablit l'ancien comportement (annoncé au démarrage, à ne pas laisser en production) | Revue de `session.breakglass_requested` / `_approved` / `_rejected` / `session.breakglass` après chaque usage ; ne pas activer `disabled` | Revue post-incident : v0.0.1 (Workflow/Approval Engine) |
| Deux comptes tenus par la même personne, ou deux personnes complices, contournent la double validation : la règle compare des identifiants, pas des humains | Un compte par personne, rôles de demande et d'approbation **disjoints**, revue des politiques `breakglass-approve:*`, provisionnement (SCIM) | Non prévue — hygiène des identités |
| ~~Aucune liste ni notification des demandes en attente~~ — **fermé** (ADR-0012) : `GET /sessions?status=pending_approval` donne à l'approbateur ce qu'il peut décider, et un webhook optionnel le prévient. Reste : **aucune nouvelle tentative** (une notification perdue est perdue, la liste est le filet), **un seul canal sans routage par personne** (les membres du canal apprennent qu'une demande existe, pour quel compte et de qui ; pas la justification), **message signé seulement si `BREAKGLASS_NOTIFY_SECRET` est fixé** (sinon l'URL est le seul secret ; Slack et Teams ignorent la signature de toute façon) — le plafond par demandeur est venu d'ADR-0013, voir la ligne suivante | Alerter sur les `session.breakglass_requested` en rafale ; revue des politiques `breakglass:*` ; canal restreint aux astreintes | Signature et plafond : fermés par ADR-0013 ; nouvelle tentative et routage par personne : Notification Service (v0.0.1) |
| Le plafond de demandes en attente est **par demandeur** (ADR-0013) : K identités qui détiennent les deux politiques occupent K × N places ; un demandeur au plafond **ne peut plus rien demander** pendant la fenêtre d'approbation (15 minutes par défaut) — un compte dont on a dérobé le jeton peut donc, en remplissant sa propre file, empêcher son titulaire de demander ; deux comptes, deux plafonds ; ~~les tentatives **refusées** ne sont pas limitées en débit~~ — **fermé pour `POST /sessions`** (ADR-0014, voir la ligne suivante) ; **un seul secret de signature, sans chevauchement de rotation** ; aucun identifiant de livraison ; aucun récepteur tiers réel n'a été essayé (le récepteur des tests est écrit d'après la description du contrat) | Alerter sur les rafales de `session.breakglass_requested` avec `success=false` ; restreindre le rôle de demande ; changer le secret des deux côtés pendant une plage calme ; vérifier côté récepteur avec la tolérance la plus courte supportable | Rotation à deux secrets : à décider |
| Le budget de `POST /sessions` est **par identité et par processus** (ADR-0014) : K jetons compromis, K budgets ; *N* réplicas du Gateway, *N* fois le budget ; un jeton volé peut **priver son titulaire** de son budget (un jeton se reforme toutes les 10 secondes avec les défauts, il va à qui arrive le premier) ; **les refus de débit ne sont pas dans l'audit**, seulement dans le journal du Gateway ; **seuls `POST /sessions`, `approve`, `reject`, `connect` et `DELETE /sessions/{id}` sont limités par identité** (ADR-0016 puis ADR-0017 pour les quatre dernières, dans un seau à part) — les lectures (dont la liste des demandes en attente, qui coûte un appel à l'Authorization Service par compte distinct) ne le sont que par adresse ; **terminer en masse est ralenti** (vingt sessions d'un coup épuisent le budget d'actions) ; **en urgence, un jeton volé pèse plus** : qui détient celui d'un approbateur ou d'un demandeur peut épuiser son budget d'actions pendant l'incident ; le budget d'actions est celui de l'utilisateur, pas d'une session (un script qui en traite vingt d'un coup est ralenti) ; valeurs par défaut choisies, non mesurées sur un usage réel | Alerter sur les lignes de journal « the session requests of user … are refused » et « the session actions of user … are refused » ; **révoquer le jeton** plutôt que relever la limite ; un état partagé (Redis) bornerait le budget entre réplicas | Budget sur les lectures (si une mesure montre une charge) ; état partagé entre réplicas : à décider |
| ~~**Les limites par adresse sont fausses derrière Traefik**~~ (ADR-0014) — **fermé si l'opérateur le règle** (ADR-0015) : avec `TRUSTED_PROXY_CIDRS` sur l'arête, chaque client réel a son seau. **Par défaut rien ne change** (personne n'est de confiance, tous les utilisateurs partagent le seau de l'adresse de Traefik ; le Gateway l'annonce au démarrage) ; **la confiance est celle de l'opérateur** : un réseau trop large laisse tout hôte qu'il contient choisir sa clé (seule la longueur 0 est refusée), et un proxy qui n'ajoute pas l'adresse qu'il voit rend l'en-tête forgeable ; **Traefik n'a pas été essayé** (les tests jouent le proxy) ; **une adresse n'est pas une personne** (NAT : un seau pour beaucoup ; beaucoup d'adresses : beaucoup de seaux, donc **aucune borne sur une force brute distribuée**) ; **le /64 IPv6 est un choix non réglable** ; **les refus par adresse ne sont ni audités ni journalisés** (visibles dans le journal d'accès de l'arête) ; par processus | Déclarer le plus **étroit** réseau possible ; faire la vérification de `docs/administration/` (login avec un `X-Forwarded-For` différent à chaque fois : la sixième tentative doit être refusée) ; régler `forwardedHeaders` de Traefik ; alerter sur les `429` du journal d'accès de l'arête | Limite par compte de login (force brute distribuée) ; protocole PROXY ; essai sur un vrai Traefik : à décider |
| ~~Une demande non décidée expire sans événement d'audit (pas de Scheduler pour le déclencher)~~ — depuis ADR-0034, le balayage du Broker la marque `expired` et écrit `session.expire` ; une décision perdante dans une course entre réplicas laisse son événement (`session.breakglass_approved` en double, `decidedBy` nomme le gagnant) | La demande, elle, est auditée ; le statut se lit `expired` ; on préfère un événement en trop à un octroi sans trace | Non prévue — choix assumé (ADR-0011) |
| ~~`terminate` n'avait ni contrôle d'appartenance ni politique propre~~ — **fermé** (ADR-0017) : le demandeur, ou une politique `session-terminate:account:{id}`. ~~**Mais terminer ne coupait pas ce qui est déjà ouvert**~~ — **fermé** (ADR-0018) : le proxy coupe les connexions et jette les tickets avant que le Broker marque la session terminée. **Il reste** : les octrois de portée du Vault ne sont pas révoqués (jeton à usage unique, réservé à l'identité du proxy, abandonné avec le ticket) ; ~~le proxy SSH est en **instance unique** (avec plusieurs réplicas, la révocation n'en atteindrait qu'un)~~ — **fermé** (ADR-0046) : le Broker connaît toutes les instances (`SSH_PROXY_URLS`), chacune annonce son adresse (`SSH_PUBLIC_ENDPOINT`), et la session est révoquée chez toutes ; une seule injoignable empêche de terminer ; la mémoire des révocations est en mémoire (perdue au redémarrage, sans danger puisque le Broker n'émet plus de ticket) ; si le proxy est injoignable on ne peut **pas** terminer (`503`, mode strict). Et `GET /sessions/{id}` reste ouvert à tout utilisateur authentifié : il montre le demandeur, le compte et la justification d'une session à qui en connaît l'identifiant | Les identifiants sont aléatoires (64 bits) ; une terminaison refusée est auditée sous le nom de l'appelant ; **n'exécuter qu'une instance du proxy SSH** ; en cas d'urgence avec un proxy en panne, couper au réseau | Révoquer aussi les octrois du Vault ; registre des proxys pour plusieurs réplicas ; mode `best_effort` optionnel ; décider qui peut **lire** une session : à décider |
| **Les refus de lecture sont audités dans une limite (ADR-0020) ; les lectures servies à un titulaire de politique le sont toutes, avant d'être servies (ADR-0021)** : un refus écrit `session.read` en échec sous le nom de l'appelant (rafale 10, puis 6 par minute, par identité et par processus ; au-delà, le refus est le même, une ligne de journal par épisode, **sans compter les refus non écrits**) ; une lecture servie à un titulaire écrit `session.read` en succès sans budget, et n'est pas servie si l'audit ne répond pas. **Il reste** : **une panne de l'Audit Service rend la lecture d'un auditeur indisponible** (le prix choisi ; le demandeur et le décideur ne sont pas touchés) ; chaque lecture écrit, sans regroupement, à la borne de la limite par adresse du Gateway ; le demandeur et le décideur ne sont pas tracés (un décideur qui a perdu son rôle relit sans trace) ; l'événement ne dit pas ce qui s'affichait ni le compte ; ~~**la liste des demandes en attente (ADR-0012) et la lecture des enregistrements divulguent sans événement**~~ : refermé par ADR-0022 et ADR-0023 (lignes suivantes) ; `404` révèle qu'un identifiant n'existe pas ; une politique `session-read:account:*` lit les justifications d'urgence de tous les comptes qu'elle couvre ; budget des refus par processus (*N* répliques, *N* fois) | Identifiants aléatoires sur 64 bits ; politiques écrites par compte ; la route du Broker n'est appelable que par le Gateway ; événement avant divulgation, signé, sous le nom de l'authentifié | ~~À décider (auditer la liste des demandes en attente)~~ fait (ADR-0023) |
| **Chaque page d'un enregistrement servie est un événement, écrit avant d'être servie (ADR-0022)** : `recording.read` en succès, ressource `session`, sous le nom de l'utilisateur que le Gateway a vérifié (celui que le client écrit est écarté), sans budget ; l'Audit Service muet ⇒ `503`, rien n'est servi, corps générique. **Il reste** : **une panne de l'Audit Service rend les enregistrements illisibles** (voulu, comme ADR-0021) ; ~~**un refus de lecture d'un enregistrement n'est pas audité**~~ (refermé par ADR-0024, plus bas) ; l'événement ne dit ni la page ni le nombre de commandes servies ; une page dont la réponse se perd après l'écriture est dans la trace sans avoir été vue ; chaque page écrit, sans regroupement, à la borne de la limite par adresse du Gateway ; **le Recorder peut désormais écrire dans la trace** (règle `emit-event` de l'Audit Service) : un Recorder compromis peut y écrire au nom de n'importe qui, comme le Broker et le proxy (les événements ne sont pas attribués par l'identité du certificat) | La route n'est appelable que par le Gateway (mTLS) ; l'identité vient du jeton vérifié ; événement avant divulgation, signé | À décider (~~auditer les refus de lecture d'un enregistrement~~ fait, ADR-0024 ; attribuer les événements à l'identité du certificat émetteur) |
| **Chaque demande servie par la liste des demandes en attente est un événement, écrit avant d'être servie (ADR-0023)** : `session.listed` en succès, ressource `session`, sous le nom de l'approbateur vérifié, pour les demandes de la page servie seulement ; un seul événement qui ne s'écrit pas ⇒ `503`, rien n'est servi ; une page vide n'écrit rien. **Il reste** : **une panne de l'Audit Service cache les urgences en attente à leurs approbateurs** (la notification ADR-0012 continue, et l'approbation d'une demande dont on a l'identifiant dépend déjà de l'audit) ; une interface qui interroge la liste écrit un événement par demande et par interrogation, sans regroupement ; les écritures sont séquentielles (au plus 100 appels avant de servir une page de 100) ; si l'écriture échoue au milieu d'une page, les premières demandes sont dans la trace sans avoir été vues ; l'événement ne dit pas que la demande a été vue *dans une liste* plutôt qu'ouverte, sinon par son nom d'action | Liste filtrée par l'autorité (ADR-0012) ; identité du jeton ; événement avant divulgation, signé | Limite acceptée |
| **Les refus de lecture d'un enregistrement sont audités dans une limite (ADR-0024)** : `recording.read` en échec sous le nom de l'appelant, rafale 10 puis 6 par minute, par identité et par processus (`RECORDING_READ_AUDIT_*`) ; au-delà, le refus est le même, une ligne de journal par épisode ; un identifiant qui ne peut pas être une session est un `400` sans événement. **Il reste** : le nombre exact de refus non écrits n'est pas enregistré ; un jeton volé épuise le budget de son titulaire ; chaque refus interroge toujours l'Authorization Service ; ~~**l'Audit Service ne borne lui-même ni la taille d'un corps ni celle d'un champ**~~ (refermé par ADR-0025) | Seau à jetons partagé (`pkg/refusalbudget`) ; route appelable par le Gateway seul ; identité du jeton | Limite acceptée |
| **L'Audit Service borne ce qu'il prend (ADR-0025)** : forme et taille de chaque champ, corps ≤ 16 Kio, `POST` seulement ; refus avant la chaîne, sans répéter la valeur. **Il reste** : ~~**le hash de la chaîne concatène les champs sans séparateur ni longueur**~~ (refermé pour tout événement écrit depuis ADR-0026, ligne suivante) ; un émetteur compromis peut toujours écrire des événements vrais dans la forme, au nom de n'importe qui (événements non attribués par l'identité du certificat) | Bornes à l'entrée ; refus fermé | Limite acceptée |
| **Le hash de chaque événement encadre chaque champ par sa longueur (ADR-0026)** : format 2 pour tout événement écrit, colonne `hash_version`, une version ne recule jamais, une version inconnue n'a pas de hash. **Il reste** : **les événements écrits avant ADR-0026 (format 1) restent sensibles au déplacement d'octets entre deux champs voisins** — l'histoire n'est pas re-hachée, ce qui détruirait la preuve qu'elle protège ; ~~**la chaîne n'a pas de clé**~~ (refermé par ADR-0027 pour toute fin de chaîne réécrite ; voir la ligne suivante pour ce qui reste) | Format canonique versionné ; vecteurs de référence calculés indépendamment | Limite acceptée |
| ~~**La clé maîtresse du Vault et du Command Recorder est locale** (`KMS_KEY_HEX`, en mémoire du processus)~~ — **fermé si Transit est configuré** (ADR-0049) : la clé vit dans le moteur Transit d'OpenBao et n'en sort pas ; le Vault scelle chaque secret sous une clé de données neuve, enveloppée par Transit ; les lignes d'avant restent lisibles tant que `KMS_KEY_HEX` est gardé. **Il reste** : sans Transit, la clé locale ; Transit devient une dépendance de tier 0 ; le jeton (fichier `0600`) se renouvelle à mi-vie (ADR-0053) et un jeton remplacé sur disque est pris sans redémarrer (ADR-0056) ; ~~pas d'AppRole~~ (ADR-0058 : le service se connecte et se reconnecte lui-même ; le jeton précédent n'est pas révoqué, un `secret_id` emballé n'est pas déballé) ; ~~pas de ré-enveloppement en masse~~ (ADR-0055 : en tâche de fond, le service dit quand `KMS_KEY_HEX` peut partir) ; un appel réseau par secret ouvert | Une politique `encrypt`/`decrypt` sur une seule clé par service ; un jeton périodique renouvelé par l'exploitant ; Transit aussi disponible que le Vault | ~~AppRole et renouvellement~~ — faits (ADR-0053, ADR-0058) |
| **La chaîne d'audit est à clé (ADR-0027)** : format 3 = HMAC-SHA256 sous `AUDIT_CHAIN_KEY_HEX` (obligatoire avec une base, hors de la base), rotation par `AUDIT_CHAIN_PREVIOUS_KEYS_HEX`, identifiant de clé et service émetteur (d'après son certificat) couverts par le HMAC. **Il reste** : ~~**une chaîne entièrement réécrite dans un format sans clé (1 ou 2), depuis son premier événement, se vérifie**~~ (refermé par ADR-0028, ligne suivante) ; **la clé est dans l'environnement du processus** : qui contrôle l'hôte de l'Audit Service la lit ; **une clé perdue rend invérifiable ce qu'elle a signé** ; ~~la troncature de la fin de la chaîne n'est pas vue par la clé seule~~ (refermé par ADR-0028 jusqu'à la dernière ancre) ; un émetteur compromis écrit toujours, à son propre nom désormais, des événements sur n'importe quelle action | HMAC ; clé hors de la base ; émetteur d'après le certificat | À décider (clé dans un KMS ; liste des actions permises par émetteur) |
| **La tête de la chaîne est ancrée hors de la base (ADR-0028)** : une ancre (événement, hash, date, sous HMAC) par période où la tête a avancé, dans `AUDIT_ANCHOR_FILE` (obligatoire avec une base) ; `verify-chain` exige chaque ancre authentique et son événement présent avec le même hash, dans l'ordre ; l'ancre nomme ce que le processus a écrit, pas ce que dit la base au moment de l'ancrer. **Il reste** : **ce qui a été écrit depuis la dernière ancre peut être tronqué sans être vu** (fenêtre = la période, 60 s par défaut) ; **quelqu'un qui écrit à la fois dans la base et dans le fichier d'ancres** (ou qui tient l'hôte de l'Audit Service, donc la clé) peut tout réécrire : le fichier doit être en ajout seul, hors de l'hôte de la base ; **un fichier d'ancres vidé** (et non supprimé) ressemble à une installation neuve ; seul un fichier local est implémenté (pas de destination distante ni WORM natif) ; le `fsync` de chaque ancre n'est prouvé par aucun test ; **l'Audit Service est en instance unique** (`docs/deployment/high-availability.md`) | HMAC des ancres ; fichier jamais recréé ; ancre = ce que le processus a écrit | À décider (destination distante en ajout seul — stockage objet WORM, journal de transparence ; vérificateur hors de l'Audit Service) |
| **Une rétention qui garde la chaîne vérifiable (ADR-0032)** : désactivée par défaut ; activée (`AUDIT_ARCHIVE_DIR`, `AUDIT_RETENTION_MONTHS` de 1 à 120), les mois entiers plus vieux que la rétention sont vérifiés, archivés hors de la base, relus, puis un point de contrôle sous HMAC est ajouté au fichier d'ancres et l'archivage est un événement `audit.archived`, avant toute suppression ; `verify-chain` repart du dernier point de contrôle, et un début de chaîne coupé sans point de contrôle reste un `409`. **Il reste** : qui tient la clé peut écrire un point de contrôle ; une archive détruite n'est plus consultable ; un binaire antérieur ne lit pas un fichier d'ancres qui contient des points de contrôle ; l'outil de vérification hors ligne d'une archive n'existe pas encore | Stocker archives et ancres en ajout seul (WORM), hors de la portée de la base | Outil hors ligne : incrément suivant |
| **Les expirations sont dans la trace (ADR-0034)** : le Broker balaie toutes les `SESSION_EXPIRY_SWEEP_SECONDS` (30 par défaut, de 1 à 3600) ; une session accordée et jamais connectée, ou une demande break-glass jamais décidée, est marquée `expired` en base, une fois quel que soit le nombre de réplicas, et `session.expire` est écrit, sans acteur, par le Broker ; un audit en panne fait attendre l'événement, jamais disparaître. **Il reste** : une panne entre l'écriture et la marque peut doubler l'événement ; l'expiration d'une demande n'est notifiée à personne ; entre l'échéance et le balayage la base dit encore `active` (le Broker répond déjà `expired`) | — | — |
| **Connexion fédérée OIDC (ADR-0035)** : code d'autorisation avec PKCE (S256), `state` et `nonce` aléatoires, à usage unique (en base) et valables 10 min ; jeton d'identité vérifié champ par champ — RS256/ES256 seulement, l'algorithme imposé par le type de la clé, `iss`, `aud`, `azp`, `exp`, `iat`, `nbf` (60 s de marge), `nonce`, `sub` ; clés du fournisseur relues au plus une fois par minute ; **les rôles ne viennent que de la table déclarée**, une identité sans rôle est refusée, le compte est `oidc:<sub>` et n'a pas de mot de passe ; tout ou rien, refus de démarrer sinon. **Il reste** : un rôle retiré chez le fournisseur reste dans le jeton OpenBastion jusqu'à son expiration (1 h) ; ni déconnexion fédérée ni jeton de rafraîchissement ; les connexions ne sont pas des événements d'audit ; une connexion fédérée compte deux fois dans le budget par adresse | Durée des jetons ; revue de la table des groupes | Audit des connexions : à décider |
| **Connexion par annuaire LDAP/AD (ADR-0061)** : `POST /auth/ldap/login`, TLS toujours (`ldaps`, ou StartTLS), certificat vérifié ; l'annuaire vérifie le mot de passe sur une connexion à part ; nom échappé, une seule entrée ; mot de passe vide refusé avant l'annuaire ; rôles par la table des groupes déclarée (par DN) ; compte `ldap:<objectGUID\|entryUUID>`. **Il reste** : **le temps de réponse trahit l'existence d'un nom** (un nom inconnu ne fait pas de bind) ; **chaque échec compte pour le verrouillage de l'annuaire** (qui connaît un nom peut consommer ses essais, au rythme du budget par adresse) ; la connexion n'est pas écrite à l'audit (comme la connexion locale et OIDC) ; les rôles valent jusqu'à la fin du jeton ; ni Kerberos, ni NTLM, ni référence suivie, un seul annuaire ; pas de groupes imbriqués en `rfc` | Politique de verrouillage de l'annuaire ; `TRUSTED_PROXY_CIDRS` derrière un proxy ; un compte de service en lecture seule | Budget par nom de connexion, audit des connexions : à décider |
